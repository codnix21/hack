Цитата (извлечено из PDF):

> При расчёте годового экономического эффекта рекомендуется учитывать амортизацию  
> капитальных затрат (CAPEX) на приобретение и внедрение роботизированных решений.  
> Команда самостоятельно:  
> - выбирает метод амортизации (например, линейный);  
> - задаёт срок службы оборудования (амортизационный период);  
> - отражает принятый метод и срок службы в допущениях к модели.  
> Для целей сравнения сценариев рекомендуется использовать единообразный подход к  
> амортизации внутри одного проекта.

Связанный контекст того же документа:

- §2.1 — базовый сценарий финансирования: собственные средства; заёмные — опционально (ставки/график не заданы).
- §2.3 — CAPEX = приобретение и внедрение; OPEX = эксплуатация.
- §2.4 — RaaS: логика платежей формируется командой; сравнение по единым KPI.

**Основное ТЗ** (`1. ФЦ БАС.pdf`, §3.5.2, с.7): формула годового эффекта —  
«сокращение текущих затрат + дополнительный доход − дополнительный OPEX».  
Амортизация в основном ТЗ **не перечислена**; добавлена рекомендацией в «Дополнениях».

### Что требует / не требует источник

| Вопрос | В источнике |
|---|---|
| Учитывать амортизацию в годовом эффекте | Рекомендуется («рекомендуется учитывать») |
| Метод | Пример: линейный; выбор за командой |
| Срок службы | Задаёт команда; числовое значение **не задано** |
| Ликвидационная стоимость | **Не задана** |
| Налоговая ставка / налоговый щит | **Не заданы** |

| База (весь CAPEX vs только оборудование) | «амортизацию … CAPEX» → трактуем как **амортизируемую базу = CAPEX сценария** |
| RaaS | Отдельной формулы амортизации арендованного актива **нет** |

**Вывод о природе показателя:** в источнике амортизация связана с **годовым экономическим эффектом** и допущениями модели. Нет оснований трактовать её как денежный отток периода или как налоговый щит без ставки налога.

## 4. Принятая методика (минимально достаточная)

### 4.1. Метод

**Линейный** (пример из источника). Иные методы не реализуются без явного требования.

### 4.2. Параметры (явные, с маркировкой допущений)

| Параметр | Ключ | Значение по умолчанию | Происхождение |
|---|---|---|---|
| Включить расчёт амортизации | `depreciation_enabled` | `true` для purchase; `true` для RaaS только на собственный CAPEX | решение команды по §2.2 |
| Метод | `depreciation_method` | `"straight_line"` | пример источника |
| Срок службы, лет | `depreciation_years` | горизонт расчёта (`years`, обычно 5) | **допущение команды** (в ТЗ нет числа) |
| Ликвидационная стоимость | `salvage_value` | `0` | **допущение** (в ТЗ нет) |
| База | — | `CAPEX` сценария после сборки breakdown | формулировка «амортизацию … CAPEX» |

Проверки диапазонов:

- `depreciation_years` ≤ 0 → амортизация неприменима, `annual = null` / ошибка валидации при явном запросе;
- база ≤ 0 → годовая амортизация = 0 (не «нет данных», а ноль базы);
- `salvage_value` > база → ошибка;
- `salvage_value` < 0 → ошибка.

### 4.3. Формулы

Пусть \(B\) — амортизируемая база (CAPEX), \(S\) — ликвидационная стоимость, \(N\) — срок в целых годах.

\[
A_{\text{год}} = \frac{B - S}{N},\quad N \ge 1
\]

График по годам горизонта \(H\): для \(t = 1..H\) начисление \(\min(A_{\text{год}}, \text{остаток})\); после \(N\) лет — 0.

Неполный год **не моделируется** (в ТЗ нет правила) — только целые годы.

### 4.4. Влияние на показатели

| Показатель | Влияние |
|---|---|
| CAPEX, OPEX | **Без изменений** (амортизация не добавляется в OPEX) |
| `annual_effect.annual_effect` (денежный / ТЗ §3.5.2) | **Без изменений** — сохраняет контрольный сценарий |
| `annual_effect.with_depreciation` | \(=\text{annual\_effect} - A_{\text{год}}\) — учёт рекомендации §2.2 |
| Денежные CF, NPV, IRR, payback по CF | **Без изменений** (амортизация ≠ денежный платёж; налог не задан) |
| TCO | **Без изменений** (не двойной учёт CAPEX) |
| Baseline | амортизация **не применяется** |
| RaaS | амортизируется только **собственный CAPEX** сценария (инфра/обучение и т.п.); арендованный парк **не** амортизируется как актив покупателя |

Округление: денежные величины — до 2 знаков (как в остальной модели).

### 4.5. Совместимость с контрольным сценарием

При тех же входах Product Readiness:

- CAPEX **53 367 600**, денежный эффект **16 068 000**, payback **3.44** — **не меняются**.
- Дополнительно появляется блок `depreciation` и `with_depreciation` (для \(N=5\), \(S=0\): \(A = 53\,367\,600 / 5 = 10\,673\,520\); accounting effect \(= 16\,068\,000 - 10\,673\,520 = 5\,394\,480\)).

Defense Rehearsal (ФОТ 281 232 000) — **другой** сценарий; не смешивать с Product Readiness.

## 5. Архитектура реализации

1. Чистый сервис `backend/app/services/depreciation.py` — без UI/импорта.
2. Вызов из `calculate_scenario` после фиксации CAPEX.
3. UI / PDF / Excel читают тот же JSON API.
4. Миграция Alembic **не нужна** — параметры в `assumptions` / `overrides` JSON.

## 6. План тестов

1. Базовый линейный пример (база, срок, год).
2. Срок ≤ 0.
3. База = 0.
4. Остаточная стоимость.
5. Горизонт > срока (нули после N).
6. Округление до копеек.
7. Отсутствие/выключение параметров.
8. RaaS: только собственный CAPEX; не «весь парк как покупка».
9. Нет двойного учёта в OPEX и CF.
10. Контрольный сценарий: CAPEX/эффект/payback без изменений.
11. API ↔ export (поля depreciation / with_depreciation).

## 7. Открытые вопросы (не блокируют выбранный минимум)

1. Нужен ли opt-in «подменять» основной `annual_effect` accounting-версией? Сейчас — **нет** (отдельное поле), чтобы не ломать KPI и payback.
2. Налоговый щит — **вне scope** до появления ставки в ТЗ/допущениях организатора.
3. Ускоренная / по компонентам амортизация — **вне scope**.
